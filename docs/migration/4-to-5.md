# Migrating from Spring Data Mirage 4.x to 5.x

## Scope

This guide covers migration from the Legacy `4.x` artifact family to the standard `5.x` artifact family.

| Property | Legacy `4.x` | Standard `5.x` |
|---|---|---|
| Group ID | `vn.com.unit.springframework.data.mirage` | `vn.com.unit.springframework.data.mirage` |
| Artifact ID | `spring-data-mirage-legacy` | `spring-data-mirage` |
| Library package | `jp.xet.springframework.data.mirage` | `vn.com.unit.springframework.data.mirage` |
| Mirage-SQL artifacts | `miragesql-legacy`, `miragesql-integration-legacy` | `miragesql`, `miragesql-integration` |
| Mirage-SQL package | `com.miragesql.miragesql` | `vn.com.unit.miragesql.miragesql` |
| Spar Wings package | `vn.com.unit.sparwings` | `vn.com.unit.sparwings` |
| Minimum Java | 17 | 17 |
| Spring baseline | Spring Boot 4, Spring Framework 7, Spring Data Commons 4.1 | Spring Boot 4, Spring Framework 7, Spring Data Commons 4.1 |

## Migration procedure

### 1. Capture the current dependency graph

```bash
mvn dependency:tree \
  -Dincludes=vn.com.unit.springframework.data.mirage,vn.com.unit.miragesql,vn.com.unit.spar-wings
```

Do not proceed while both Legacy and standard artifacts are present.

### 2. Replace the dependency

```xml
<dependency>
    <groupId>vn.com.unit.springframework.data.mirage</groupId>
    <artifactId>spring-data-mirage</artifactId>
    <version>5.0.0</version>
</dependency>
```

If the application declares Mirage-SQL directly, remove the `-legacy` suffix and keep all Mirage-SQL modules on the same target version.

### 3. Update packages

Replace Spring Data Mirage and Mirage-SQL package references in Java source, Spring XML, configuration, reflection, and serialization metadata:

```text
jp.xet.springframework.data.mirage  -> vn.com.unit.springframework.data.mirage
com.miragesql.miragesql            -> vn.com.unit.miragesql.miragesql
```

Use repository-wide searches to find both compiled and string-based references:

```bash
rg 'jp\.xet\.springframework\.data\.mirage|com\.miragesql\.miragesql' src
```

The `http://www.springframework.org/schema/data/mirage` XML namespace URI remains unchanged.

### 4. Move SQL resources with repository interfaces

SQL resources are resolved relative to repository packages. When a repository interface moves from `jp.xet...` to `vn.com.unit...`, move its base and method-specific SQL files to the matching resource directory.

Verify at least:

```text
RepositoryName.sql
RepositoryName_methodName.sql
```

### 5. Verify API usage

Compile and review repository interfaces, return types, pagination, chunking, modifying queries, auditing, and custom factory configuration. Replace unsupported asynchronous return types with supported alternatives such as `CompletableFuture` where applicable.

### 6. Test the application

At minimum, verify:

- dependency convergence and absence of Legacy artifacts
- application startup and repository scanning
- transaction commit and rollback
- CRUD and modifying queries
- base and method-specific SQL resource resolution
- paging, sorting, chunking, and batch operations
- optional, collection, and single-result behavior
- auditing configuration
- database-specific SQL, identifiers, types, and JDBC drivers
- representative concurrent and performance workloads

### 7. Roll out and roll back

Deploy through the application's normal staged rollout. Monitor repository initialization, SQL-resource errors, transaction failures, database errors, latency, and connection-pool behavior.

Rollback restores the previous application artifact and its complete Legacy dependency set. Do not roll back only Spring Data Mirage while leaving standard Mirage-SQL artifacts in place.
